# AGENTS.md

This file governs how AI coding assistants (Claude, Copilot, Cursor, Gemini, ChatGPT,
Devin, or any other LLM-based tool) and human contributors are expected to work in this
repository. It applies to every branch, every commit, and every pull request, regardless
of who or what typed the first draft.

It exists for one concrete, practical reason: this project intends to submit to
[extensions.gnome.org](https://extensions.gnome.org) (EGO), and EGO has a written,
enforced rule against AI-generated submissions. Anyone opening a PR here, human or agent,
should read this before writing a line of code.

## The rule this project is built around

From GNOME's own [Extension Review Guidelines](https://gjs.guide/extensions/review-guidelines/review-guidelines.html#extensions-must-not-be-ai-generated)
(in force since December 2025):

> Extensions must not be AI-generated
>
> While it is not prohibited to use AI as a learning aid or a development tool (i.e. code
> completions), extension developers should be able to justify and explain the code they
> submit, within reason.
>
> Submissions with large amounts of unnecessary code, inconsistent code style, imaginary
> API usage, comments serving as LLM prompts, or other indications of AI-generated output
> will be rejected.

Related precedent this project follows the spirit of:

- [Loupe's contribution guidelines](https://discourse.gnome.org/t/loupe-no-longer-allows-generative-ai-contributions/27327):
  *"This project does not allow contributions generated by large language models (LLMs)
  and chatbots."*
- [GNOME Calendar's no-LLM statement](https://discourse.gnome.org/t/gnome-calendar-takes-a-step-further-with-artificial-intelligence-ai-contributions/35952),
  adopted after receiving merge requests that were "clearly generated."
- GNOME Circle's app-review criteria, which mirrors the Shell extension policy above.
- Flathub's policy, which is stricter still: it rejects apps containing AI-generated *or*
  AI-assisted code, docs, manifests, patches, or build scripts, including materials beyond
  the extension code itself. If this project ever targets Flathub distribution, assume
  that bar applies too.

The rule is not "no AI tools ever." Autocomplete, refactoring suggestions, and using an
LLM to learn an unfamiliar API are explicitly allowed. The line is **understanding and
accountability**: a human maintainer must be able to explain and take responsibility for
every line that ships, without reading it off a chat log.

## What this means operationally

### For AI coding agents working in this repo

1. **Never invent an API.** Every GNOME Shell / GJS / Clutter / St / GLib / Gio / Adw /
   Gtk call you use must be verified against real documentation
   ([gjs-docs.gnome.org](https://gjs-docs.gnome.org)) or existing working code in this
   repo, not pattern-matched from a vague memory of "this looks about right." If you are
   not sure a method exists, say so explicitly instead of guessing. Plausible-sounding
   wrong names (e.g. `Main.layout` instead of `Main.layoutManager`) are exactly the
   failure mode reviewers are told to look for, and this project has already shipped that
   exact bug once.
2. **No LLM-prompt comments.** Never leave comments like `// TODO: implement this
   properly` written as if to a future model, or comments that describe what you were
   asked to do rather than what the code does.
3. **Match existing style.** Don't reformat, reindent, or restructure code outside the
   diff's actual purpose. Run the existing lint/validation steps (below) before proposing
   a change.
4. **Justify every non-trivial change in plain language**, in the commit message or PR
   description, written so a human who didn't watch you write it can verify your
   reasoning. If the only justification is that it "should work," don't submit it.
5. **Flag uncertainty instead of hiding it.** If you are not confident an API call, a
   timing assumption, or a GNOME Shell version behavior is correct, say so in the PR
   description rather than presenting it with false confidence. A flagged guess a human
   can double-check is fine; a confident wrong answer is not.
6. **Don't pad.** No unnecessary abstraction layers, defensive code for cases that can't
   happen, or comments restating what a function does. EGO reviewers are explicitly
   instructed to reject "large amounts of unnecessary code."

### For human contributors (including the maintainer)

1. You may use AI tools to draft, learn, or explore. That's allowed under the EGO rule.
2. Before merging anything AI-assisted, **read it line by line and be able to explain it
   without the tool present.** If you can't explain a chunk of code, that's a signal to
   either rewrite it yourself or cut it, not to ship it anyway.
3. Test on a real GNOME Shell session (nested session first, see `README.md`) before
   claiming something works. Don't merge on "the syntax check passed."
4. Keep commit history honest: if a commit was AI-drafted and then reviewed/edited by a
   human, that's fine and doesn't need special disclosure. If a whole feature was
   generated and merged without real review, that's the thing this file exists to
   prevent.

## Definition of done (checklist before opening a PR)

- [ ] Every API call used exists, checked against
      [gjs-docs.gnome.org](https://gjs-docs.gnome.org) or working precedent, not memory.
- [ ] `node --check` (or equivalent) passes on every changed `.js` file.
- [ ] `glib-compile-schemas schemas/` succeeds if any schema changed.
- [ ] `xmllint --noout` passes on any changed XML.
- [ ] Tested in a live GNOME Shell session (nested `gnome-shell --nested --wayland` at
      minimum), not just syntax-checked.
- [ ] No stray comments, dead code, or unused variables left behind.
- [ ] Style matches the surrounding file (see GNOME's
      [ESLint rules](https://gitlab.gnome.org/GNOME/gnome-shell-extensions/tree/main/lint)).
- [ ] The author (human) can explain every changed line without re-reading a chat
      transcript.

## Where this repo currently stands

Large parts of this extension's initial implementation were drafted with heavy AI
assistance while its architecture was being worked out. That history doesn't disappear
because this file now exists. Before any submission to extensions.gnome.org, the plan is
to go through the codebase deliberately: understand it, test it, and rewrite what needs
rewriting, until every part meets the bar above. This file records that intent and the
standard future changes are held to. It is not a claim that the current code has already
cleared it.

## Build & validate commands (for agents and humans alike)

```bash
# Syntax-check a JS file (ES module aware)
cp extension.js /tmp/check.mjs && node --check /tmp/check.mjs

# Validate + compile the GSettings schema
xmllint --noout schemas/*.gschema.xml
glib-compile-schemas schemas/

# Install locally for testing
make

# Test safely without risking the main session
dbus-run-session -- gnome-shell --nested --wayland
```
